# Worker Optimizer 0.2.1-hotfix.1

Pre-release for in-game testing. The complete automated Blueprint test suite,
full cook and package checks passed on 6 October 2026. Shipping-game acceptance
of this hotfix is pending.

This hotfix addresses assignment runs that kept showing activity after the
game failed to confirm an assignment command.

## Changes

- Manual and scheduled runs, including day start, use the same bounded
  recovery path. A confirmed late result can trigger replanning within the
  existing two-replan limit.
- An unresolved command receives its original 10-second confirmation deadline
  plus 10 seconds of recovery grace. Each processing tick checks for a result
  before the cutoff. If it remains unresolved, the run publishes a failed
  report and stops the busy animation.
- The pending command is never resent blindly. The start button remains locked
  until that command is confirmed or the world is reloaded. A late receipt
  after closure does not resume the old action queue or rewrite its report.
- Corrected the `bridge.guard` prefix check so validated state rejections
  before dispatch can trigger replanning.
- Timeout diagnostics now include action, worker ID, building ID and slot.

Priorities, builder reserve, scheduling settings and processing budgets are
unchanged. Confirmed assignment changes are retained when a run fails.

## Validation and Limits

Automated coverage includes late-confirmation recovery, manual and day-start
timeouts, immutable failed reports, no duplicate dispatch, retained admission
locks, delayed unlock, missing observation data, UI status and scheduling.
See the [verification record](https://github.com/repte/whiskerwood-worker-optimizer/blob/main/docs/verification/2026-10-06-assignment-hotfix.md).

The cause of the reported native assignment no-op in the affected save has
not been proved. This hotfix adds recovery and a visible failure outcome; it
does not establish that every native rejection can be recovered.
